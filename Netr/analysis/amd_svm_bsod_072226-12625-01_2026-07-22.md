# AMD SVM startup BSOD analysis

## Evidence

- Dump: `test-package/072226-12625-01.dmp`
- Dump SHA-256: `14DE9F3F89761186FFC211D261D5C97F86F6DEED1E8ABDF2F725DE5E16FD0C6E`
- Debug session time: `2026-07-22 19:53:48 +08:00`
- Driver image/PDB timestamp: `2026-07-22 19:19:12`
- Bugcheck: `0x1E KMODE_EXCEPTION_NOT_HANDLED`
- Exception: `0xC0000005`, write to `0x578`
- Fault: `GuardMetaCore!AsmSvmLaunch+0xB4`, `AsmSvm.asm:318`

The matching private PDB resolves the faulting instruction to
`mov [r8 + 578h], rcx`. The dump arguments show a write to `0x578`, so `r8`
was zero.

## Root cause chain

1. Latent defect: `AsmSvm.asm` hard-coded `VCPU_DATA.Vmcb` as `0x50` and
   `VmcbPhysical` as `0x58`.
2. First regressing design decision: Intel-only `Vpid`, EPT PEB-spoof and
   classification fields were inserted before the AMD fields in the shared
   `VCPU_DATA`, but the AMD assembly offsets were not updated or guarded by
   compile-time checks. The defect is already present in the backup baseline
   and the initial imported Git revision.
3. Runtime trigger: AMD startup called `SvmLaunchVm` and entered
   `AsmSvmLaunch` on the first processor.
4. Amplifier: none is required; the failure is deterministic before the first
   `VMRUN`. The all-processor startup loop only exposes the first bad launch.
5. Final mechanism: the current PDB reports `Vmcb=0x88` and
   `VmcbPhysical=0x90`. Reading `VcpuData+0x50` returned the VPID/padding area
   as a null pointer, then the VMCB RIP write dereferenced `0+0x578`, producing
   bugcheck `0x1E`.

Unreal has CPU-vendor recognition but no SVM/VMCB/VMRUN implementation to use
as a semantic baseline for this path.

## Fix scope

- `AsmSvm.asm`: changed only AMD `VCPU_DATA` VMCB offsets to `0x88/0x90`.
- `HvVmcb.c`: added AMD-only compile-time layout contracts for the VCPU and
  VMCB fields consumed by assembly.
- `HvVmcb.c`: rejects null, misaligned or zero-physical-address launch
  contexts before entering assembly.
- No VMX, EPT or Intel runtime code was changed.

## Rollback point

Pre-fix hashes:

- `AsmSvm.asm`: `B8177816B46F4134709B1BDA39BAE9914C012B2508672AAA6694A25F3FC0B056`
- `HvVmcb.c`: `E5B81C0D429B80F48FA5A1E6B2C59176F1038CB1E819DBC667B0EF72F9E8A557`

Rollback must remove only the focused hunks in these two files; neither file
should be replaced wholesale because `HvVmcb.c` contains unrelated prior
working-tree changes. Reverting the offsets to `0x50/0x58` intentionally
restores the proven startup crash and is only a forensic rollback point.
